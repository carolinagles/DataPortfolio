Madrid Restaurant Intelligence

Can 1.16 million reviews become a tool that diagnoses a restaurant, compares it with its peers and explains what reviewers say?

0.808

macro F1 of the review classifier on 996 restaurants kept out of development

restaurants diagnosed
10,056
peer groups
55
Spanish / English macro F1
0.809 / 0.793

Why the result holds

The split was made by restaurant, so none appears in both development and test. Validation gave 0.812 and the single test run 0.808: the score held on unseen data. A model that always answers “Positive” reaches 0.287.

Three notebooks, one pipeline

Each notebook reads the previous one's files and writes the next one's, so the analysis can be rerun end to end.

  1. 01_data_cleaning.ipynb

    Data cleaning

    Turns the raw TripAdvisor export into one trusted table.

    • Converts hidden missing codes into real missing values: user IDs of −1, empty titles, empty price and cuisine lists, restaurant ratings of −10.
    • Rescales ratings from 10–50 to 1–5 and removes 8,608 duplicate reviews.
    • Keeps Spanish and English reviews and labels them: 1–2 stars Negative, 3 Neutral, 4–5 Positive.
    • Checks every exported column with a Pandera schema.

    Output1,157,800 reviews from 10,056 restaurants, saved as Parquet.

  2. 02_exploratory_data_analysis.ipynb

    Exploratory analysis and preparation

    Measures the data and builds the products the app reads.

    • Finds the class imbalance (74.71% Positive), text length (median 45 words) and language mix (82.8% Spanish).
    • Builds a diagnosis for every restaurant and 55 peer groups by cuisine and price, each with at least 30 restaurants and 1,000 reviews.
    • Compares two six-month windows: 1,017 restaurants have enough reviews to evaluate and 199 show a deterioration signal.
    • Splits the text corpus by restaurant for modeling and saves every rule in a shared configuration file.

    OutputDiagnosis, peer-group and corpus files in Parquet, plus project_config.json.

  3. 03_modeling_and_productization.ipynb

    Modeling and productization

    Selects the text classifier and packages it for the app.

    • Compares a majority baseline, logistic regression and LinearSVC on 60,000 bilingual TF-IDF features.
    • Tunes LinearSVC on validation, then scores the test restaurants a single time.
    • Logs 14 runs in MLflow and checks that the reloaded model predicts exactly like the trained one on 1,000 reviews.
    • Reports results separately for Spanish and English reviews.

    OutputA 2 MB scikit-learn pipeline with its metadata and metrics.

The app

The notebooks become a Streamlit app for anyone who wants to understand a restaurant's reputation without reading code. It works on historical data up to June 2023.

Restaurant diagnosis
Pick a restaurant and read it in three tabs: an overview with up to three prioritized checks, each with its evidence and a way to measure improvement; a peer comparison that ranks it against restaurants of the same cuisine and price; and historical alerts, which need both a rating drop and a rise in negative reviews to cross a threshold.
Market and Top 10
Rank a peer group by six measures. The adjusted rating adds 30 average reviews to every restaurant, so 40 excellent reviews do not outrank 2,000 almost-as-excellent ones.
Review classifier
Type a review in Spanish or English and get the label, how far it leads the next label and the exact contribution of each word.

Pump It Up

Can recorded water-point characteristics flag pumps that are broken or need repair?

0.8186

mean 5-fold cross-validated accuracy with LightGBM, ±0.0022

labeled water points
59,400
model features
53
predictions submitted
14,850

Why the result holds

Always predicting “functional” scores 0.543. The five cross-validation folds agree within ±0.002, so the estimate is stable.

How we got there

  1. Merge and audit

    Training data, labels and test joined on id: 74,250 rows, no duplicate ids. Columns repeating the same information at another level of detail were dropped.

  2. Keep missing values informative

    Missing funder, installer and scheme management became “unknown”; permit and public meeting took the mode.

  3. Engineer features

    Pump age, distance to the country centre, a latitude–longitude interaction, regional pump density and presence flags.

  4. Encode without leakage

    Target encoding for 10 high-cardinality columns, fitted on training rows only; one-hot encoding for the rest.

  5. Tune and choose

    Optuna ran 50 LightGBM and 30 CatBoost trials. LightGBM was kept for the higher validation score: 0.8189 against 0.8170.

Evidence

Limits

“Needs repair” is 7.3% of training labels but only 3.9% of submitted predictions, so the model under-detects it. The 0.90 report inside the notebook is not independent: the model was refit on all labeled rows before scoring.

Built with

Python, pandas, scikit-learn, LightGBM, CatBoost, Optuna

Glucose Tolerance

Does baseline glucose differ between young and adult patients, and how closely does it predict the 60-minute value?

+4.71

mg/dL higher mean baseline glucose in adults, 95% CI 0.70 to 8.72

Pearson r, young group
0.796
R², linear model
0.634
RMSE
4.61 mg/dL

Why the result holds

Normality and equal variances were checked before the t-test, so its assumptions hold. The interval excludes zero and p = 0.022. In the young group, baseline glucose explains 63% of the 60-minute variation.

How we got there

  1. Describe each group

    Central tendency, dispersion and shape. Adults show a higher, more concentrated baseline; the young group is multimodal.

  2. Check assumptions

    Shapiro–Wilk suits groups under 50; Q–Q plots and Levene's test confirm the conditions for parametric tests.

  3. Compare the groups

    Confidence interval and t-test for the difference in baseline means.

  4. Model the relationship

    Pearson correlation and a linear regression of 60-minute on baseline glucose in the young group.

  5. Estimate a proportion

    Share of patients above 95 mg/dL, with a 98% interval and a test against 15%.

Evidence

Limits

65 records: 35 young patients and 30 adults. Results describe this sample and are not clinical conclusions.

Guess the Number

How do you rebuild a console guessing game as a modular Python web app?

6

Python files, each with one job, so the rules can change without touching the screen

secret number

game kept between reruns
st.session_state
saved games and records
openpyxl + pandas

How the code is organized

The game logic lives in plain Python functions that read and change one dictionary. Streamlit only draws that dictionary, so the rules never depend on the interface.

How the game is built

  1. Write the rules as data

    Difficulty levels, scoring, hint cost and heat levels are dictionaries and tuples in settings.py. Changing a rule means editing one value.

  2. Keep the game in one dictionary

    new_game() returns the secret number, attempts left, the possible range, the history and status flags. It is stored in session state, so it survives every Streamlit rerun.

  3. Validate before counting

    play_turn() rejects empty, out-of-range and repeated guesses before using an attempt, then narrows the range and records the move.

  4. Update before drawing

    Buttons call functions through on_click, which run before the page redraws. The display is never one move behind.

  5. Draw from the state

    ui.py turns the dictionary into the screen, range bar and heat meter. Player names are escaped, since they come from users.

  6. Save and analyse

    openpyxl appends each game to Excel. pandas reloads it, recalculates scores with the same function and builds the leaderboard with groupby; Matplotlib draws the charts.

Evidence

Limits

Records live in an Excel file. On Streamlit Community Cloud the file system resets when the app restarts, so saved games can be lost; a database would fix it.

Built with

Python (random, datetime, pathlib, html), Streamlit, pandas, Matplotlib, openpyxl

Hostname Generator

How do you turn a hostname-naming exercise into a tool that generates and decodes server names on demand?

8

characters encode four parts: AIGER789 reads as AIX, Integration, Germany, node 789

hostnames per request
1 to 5,000
keyword position
Anywhere
download, plus copy per row
CSV

Why the names follow the rules

Every part is drawn with the weights set in the code: Ireland 30%, Germany 23% and Norway 6% for countries, Linux 40% for operating systems. When a keyword is fixed, the app keeps those weights and only discards names that can't contain it.

The app

The notebook proved the naming rules; the app turns them into a tool anyone can use to create and read hostnames.

Open Hostname Generator ↗
Generate
Choose how many hostnames you need, from 1 to 5,000, and an optional keyword such as IRL, LP or 007 that must appear in every name. Enter submits the form.
Results
A numbered list with the keyword highlighted and each name decoded into OS, environment and country. Copy one name, copy all of them or download a CSV.
Distribution
The share of each OS, environment and country in the current result, to check it against the configured weights.

How the app was built

  1. Prototype in a notebook

    Weighted random draws for each part, 1,500 hostnames decoded by position into five columns, exported to CSV and checked with charts.

  2. Move the logic to a module

    hostnames.py holds the code tables, generation, validation and decoding. The interface only imports it, so the rules live in one place.

  3. Add the keyword

    The generator tries every position where the keyword fits, keeps the codes compatible with it and weights each position by its probability. Impossible keywords are rejected before generating.

  4. Keep names unique

    Duplicates are skipped up to an attempt limit. If a keyword allows fewer names than requested, the app lists all of them and says so.

  5. Design the interface

    A one-column layout with numbered sections. Results are an HTML component with per-row copy buttons and a fallback when the clipboard is blocked.

  6. Deploy

    Code on GitHub, theme in .streamlit/config.toml, app on Streamlit Community Cloud. Every push to main updates it.

Evidence

Limits

Simulated data with fixed code tables. It tests the naming logic, not a real server estate, and node numbers are drawn uniformly.

Built with

Python (random, pandas), Streamlit, HTML and JavaScript component, Jupyter
